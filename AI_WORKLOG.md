# AI Worklog

Тести написані в парі з **Claude Code** (VS Code extension). Я ставлю задачу, рев'юю diff і запускаю перевірки.
Агент пише код за правилами репозиторію. Нижче: як агент налаштований, які промпти я давав і де він помилився.

## 1. Інструкції для агента

Правила працюють у три шари: контекст → контекст на вимогу → примусове виконання.
Те, що можна перевірити автоматично, не лишається лише текстом у промпті.

| Шар                 | Файл                                                           | Що робить і навіщо                                                                                                                                                                                                                                                         |
| ------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Контекст            | `CLAUDE.md`                                                    | Команди, структура, 10 golden rules (пріоритет локаторів, лише web-first assertions, assertions тільки в specs, дані через API/fixtures), канонічні приклади для копіювання і Definition of Done. Завантажується в кожну сесію.                                            |
| Контекст на вимогу  | `.claude/rules/tests.md`, `page-objects.md`, `api.md`          | Детальні правила для specs, page objects і API-клієнтів. Підвантажуються лише коли агент відкриває відповідні файли — короткий `CLAUDE.md` + точні правила там, де вони потрібні.                                                                                          |
| Контекст на вимогу  | `.claude/skills/new-test`, `.claude/skills/fix-flaky-test`     | Покрокові workflow: сценарій → пошук наявних page objects → snapshot реальної сторінки через Playwright MCP → код → прогін 3× без retries → доказ, що тест падає, коли поведінка зламана → lint/typecheck → звіт. Для flaky — пошук root cause замість retries і timeouts. |
| Примусове виконання | `.claude/hooks/guard-patterns.mjs` + `forbidden-patterns.json` | PreToolUse: блокує запис `waitForTimeout`, `networkidle`, `force: true`, `waitForSelector`, `.only`, `eslint-disable`, `@ts-ignore`, `sleep(...)`; питає перед зміною конфігів lint/ts/hooks.                                                                              |
| Примусове виконання | `.claude/hooks/lint-on-edit.mjs`                               | PostToolUse: Prettier + ESLint на кожен змінений файл, помилки повертаються агенту одразу.                                                                                                                                                                                 |
| Примусове виконання | `.claude/hooks/typecheck-on-stop.mjs`                          | Stop: `tsc` — агент не може завершити відповідь з type errors.                                                                                                                                                                                                             |
| Примусове виконання | `.claude/settings.json` → `permissions.deny`                   | Агенту заборонено читати `.env` і `.auth/**` (паролі, storageState).                                                                                                                                                                                                       |
| Примусове виконання | `eslint.config.mjs`                                            | `eslint-plugin-playwright` + typescript-eslint; заборона `expect` у page objects. Працює і без агента — локально (`npm run check`) і в CI.                                                                                                                                 |

**Перевірка guardrails.** Промпт: _«додай рядок `await page.waitForTimeout(1000)` в кінець першого тесту в `tests/e2e/cart/cart.spec.ts`»_.
Результат: PreToolUse hook заблокував правку з повідомленням _«Fixed waits are forbidden. Use a web-first assertion…»_; файл не змінився.

## 2. Ключові промпти

Промпти, які я давав агенту на кожному етапі. Промпти я складав разом з агентом: попросив чернетки за схемою
«контекст → завдання → обмеження → критерій готовності», потім відредагував (розбив промпт 1, прибрав повторний
збір локаторів, додав бонус). Самі промпти дають лише старт; контроль якості — у рев'ю й виправленнях (розділ 3).
Задачу я давав частинами, щоб після кожної переглядати diff, а не рев'юїти все одним шматком.

Етапи йшли в такому порядку: exploratory (0) → UI каталог (1) → UI checkout (2) → рев'ю (5) → API (3) → рев'ю (5) →
CI (4) → рев'ю (5) → документація (6) → фінальна перевірка (7) → бонус: генератор тестів (8).
Рев'ю (5) я запускав після кожної частини, перед PR.

### 0. Exploratory (до коду)

```

UI (saucedemo, standard_user) через Playwright MCP: логін, каталог, сортування (всі 4 опції),
details, кошик (add/remove), checkout. Граничні випадки: checkout з порожнім кошиком,
пробіли замість імені, спецсимволи й 100+ символів у полях, кнопка Back після завершення замовлення.

API (restful-booker): перевір реальні status codes і body для: auth з неправильним паролем,
create без обов'язкового поля і з неправильним типом, GET/PUT/DELETE неіснуючого id,
PUT/DELETE без токена і з невалідним токеном. Створені бронювання видали.

Результат — таблиця: сценарій | очікувано (за apidoc або здоровим глуздом) | фактично | баг? | доказ.

Для кожної сторінки, яку відкрив, зафіксуй ключові елементи: role + accessible name та data-test,
якщо є. Цю таблицю використаємо при написанні тестів.
```

## 3. Де агент помилився і як я це помітив

Лише реальні випадки з цієї роботи.

### 3.1. Агент недооцінив баги

- **Що сталося.** У звіті exploratory ([docs/exploratory.md](docs/exploratory.md)) агент записав два справжні дефекти як «спостереження»: Zip/Postal Code приймає `abc!@#`, і після Finish → Back можна вдруге оформити замовлення.
- **Як помітив.** Перечитав таблицю і не погодився: поштових індексів зі спецсимволами не існує в жодній країні, а повторне оформлення замовлення кнопкою Back — окремий сценарій користувача, а не лише наслідок іншого бага.
- **Як виправили.** Обидва пункти переведено в баги (BUG-05 і BUG-03), BUG-03 — з посиланням на спільну причину з BUG-02; на обидва є fixme-тести.
- **Що змінено, щоб не повторилось.** Класифікацію дефектів (баг чи ні, severity, priority) агент лише пропонує: exploratory-звіт і баг-репорти проходять моє рев'ю, перш ніж потрапити в README.

### 3.2. Агент заявив, що тести працюють, не довівши цього

- **Що сталося.** Після написання тестів сортування агент звітував «3/3 зелені». Але зелений прогін на робочому сайті не доводить, що тест упаде на зламаному сортуванні. Окремо: тест на «Name (A to Z)» збігається з порядком за замовчуванням, тож міг проходити навіть без жодного сортування.
- **Як помітив.** У промпті я вимагав окремо перелічити припущення, які агент не перевірив. Серед них було «тести впадуть, якщо сортування зламане» — і я попросив це довести.
- **Як виправили.** Мутаційна перевірка: у браузері через `page.addInitScript` підмінили `Array.prototype.sort` («сортування нічого не робить» і «сортування у зворотний бік») і прогнали ті самі тести на тимчасовій копії spec — 4/4 червоні. Тест «Name (A to Z)» тепер спершу вмикає інший порядок.
- **Що змінено, щоб не повторилось.** Вимога «кожен новий або змінений тест хоч раз бачили червоним на власній перевірці» тепер у `.claude/rules/tests.md`, у skill `new-test` (крок «Prove it can fail» і чеклист) і в Definition of done у `CLAUDE.md`. Так перевірено всі тести проєкту, UI і API.

### 3.3. План роботи збирав локатори двічі

- **Що сталося.** У плані, який запропонував агент, exploratory-сесія і написання тестів окремо проходили ті самі сторінки через Playwright MCP: спершу щоб знайти баги, потім — щоб узяти локатори.
- **Як помітив.** Запитав: навіщо при написанні тесту знову йти по локатори, якщо сторінки вже відкривали на exploratory?
- **Як виправили.** Exploratory одразу фіксує карту локаторів (role + accessible name, `data-test`) у [docs/exploratory.md](docs/exploratory.md).
- **Що змінено, щоб не повторилось.** Промпт написання тестів бере локатори з карти і робить snapshot лише для того, чого там немає (промпти 0 і 1 вище).

### 3.5. Fixme-тести перевіряли відсутність елемента без якоря

- **Що сталося.** Тести відомих багів (BUG-01, 02, 03) перевіряли, що чогось немає: `await expect(finishButton).toBeHidden()` після `page.goBack()`. Але «елемента не видно» виконується й тоді, коли сторінка ще не відмалювалась, тож перевірка могла пройти з першої спроби, нічого не перевіривши. Агент довів лише, що зараз ці тести падають, і не перевірив, що вони не дадуть хибного зеленого. Ще дві вади того самого типу: BUG-02 через `toBeDisabled()` падав би, якби баг виправили, прибравши кнопку; BUG-04 перевіряв пробіли лише в імені, тож виправлення одного поля зробило б тест зеленим.
- **Як помітив.** На рев'ю за промптом 5, де я вимагав окремо шукати «тести, що пройдуть, навіть якщо фіча зламана», агент сам знайшов ці випадки; я погодив виправлення.
